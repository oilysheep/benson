## 1. Objective, scope, and acceptance boundary

Bring the existing Benson control plane into conformance with the approved architecture while preserving correct domain implementation. This plan replaces the previous stage instructions in this same file. Historical stage names identify evidence only; P01–P11 are the sole prospective execution sequence.

The target is one native canonical conversation across Main/direct execution, bounded admission-consistent routing context, deterministic continuation before ordinary routing, independently recorded admissions sharing one workflow final, isolated activations, explicit agent capacity and separate resource ownership, one globally enforced completion protocol, and one interactive outbound gate using native delivery/recovery.

Architecture owns responsibilities and semantics. This plan owns implementation sequencing, component dispositions, compatibility/migration obligations, evidence, and acceptance. Logical owners named here do not authorize a new plugin, tool, service, store, configuration surface, or core modification. Exact unsupported native bindings remain UNKNOWN with dependent work blocked; naming a desired API is not an implementation decision.

This documentation-only rewrite authorizes no runtime or implementation change, including code/configuration/agent/tool/patch modification, deployment, service restart, provider call or device action. Approval of this plan does not authorize starting a future implementation stage.

Whole-plan acceptance requires all Section 27.4 gaps, the stage criteria, and the mandatory acceptance matrix below to have observed evidence. Source tests, a snapshot, disabled production flags, or acceptance of one limited cohort cannot establish production conformance. Real direct routing needs an accepted real Decision capability; the positive conditional workflow needs independently verified exact Jessica task completion. UNKNOWN or a blocked mandatory capability keeps the dependent route and whole-plan closure incomplete.

Out of scope: unrelated domain expansion, rewriting correct legacy Python, heartbeat investigation, general model-fallback redesign, recovery-artifact cleanup, additional frameworks/transports/stores, and implementing Jessica's missing physical capability in this plan. ## 3. Terminology, canonical owners, and transitions

### 3.1 Terms used throughout this plan

| Term | Single meaning |
| --- | --- |
| External admission | One trusted adopted external input with exact source text and provenance. Duplicate delivery/retry of that input retains its identity. Identical text in two genuine turns is two admissions. An admission may join an existing eligible workflow or receive a new route. |
| Canonical conversation | OpenClaw-owned external history and authorized address/requester binding spanning Main/direct execution. It retains each admission and the correlated workflow final independently of the executing agent. |
| Session | Native context/transcript identity with generation/reset semantics. An external conversation binding, an agent-scoped session key and an isolated execution session are not interchangeable. |
| Run / activation | One native execution instance under a particular agent identity and permissions. A new domain activation is fresh and isolated. An authorized native resume may use a successor run; it preserves the nonterminal workflow rather than reviving a terminal run. |
| Workflow | Trusted ownership/correlation for admitted intent, tasks, continuations and its final response. Its native binding tracks admission membership, accepted-intent revision, lifecycle and completion/delivery references. It may span runs; it is not a new Benson database. |
| Commitment | Deterministic assignment of an admission to one authorized workflow action or initial Main/direct execution path. It is not domain success, intent application, completion acceptance or delivery. |
| Continuation | An authorized action on eligible active/pending work. External admission continuation, native caller continuation after a child result, and pending-task resume are distinct event types with their own authority. None is terminal repair. |
| Accepted intent | Ordered user intent admitted into the workflow. Admission does not prove consumption or application; final facts must report amendments that were not applied or remain uncertain. |
| Completion | A validated canonical domain-task or final-workflow protocol record, including an evidence-preserving FAILED report. Completion outcome and business/physical outcome are separate. |
| Terminal finalization | Entry into the one run-terminal protocol. For the final semantic owner of a workflow it atomically closes admission membership/intent before candidate validation. Rejection enters restricted repair; acceptance or runtime reconstruction/reporting settles the terminal record. |
| Shared final | Exactly one final-workflow completion and one logical final interactive delivery for the workflow's closed membership, reflecting the latest accepted intent and verified effects/limitations. Joined admissions do not own separate finals. |
| Transport freeze | Later immutable binding of approved message, prepared provider units and authorized delivery target before native queue custody. It is not the admission-join cutoff. |
| Delivery | Native provider outcome for the workflow's frozen final identity. Canonical transcript append, queue custody and send acknowledgment are separate evidence. Unknown/partial send is not delivered or safe to resend blindly. |
| Queue | Always qualified: native input queue, reviewed capacity wait/queue policy, or native outbound delivery queue. Input custody/acknowledgment is not execution or guaranteed restart replay. No new queue owner is created. |
| Recovery | Explicitly qualified native continuation reconciliation, completion reconstruction/phase recovery, domain-effect reconciliation, or native frozen-delivery recovery. Each stays with its existing owner; none silently replays domain execution. |
| Agent capacity / resource ownership | Capacity bounds active executions of an agent identity across all entry paths. Resource ownership authorizes mutation of a particular device/domain resource and rejects stale actors. A finished run does not establish physical-resource release. |

### 3.3 Control flow and irreversible boundaries

```text
native exact admission + canonical conversation custody
  -> bounded authorized context + trusted workflow/capacity facts
  -> optional one-shot Decision evidence
  -> deterministic eligible-continuation check
       -> join/continue or authorized pending resume/wait/reject
       -> otherwise ordinary Main/direct routing and single commitment
  -> authorized execution under capacity and domain resource policy
  -> final semantic owner enters terminal protocol: close membership/intent
  -> validate candidate; reject -> completion-only repair (execution closed)
       -> NORMAL, or runtime RECOVERED / FAILED from retained evidence
  -> Completion Control: CALLER, or final-workflow/direct projection
  -> Response Controller: eligibility and owner message / narrow fallback
  -> native prepare -> freeze -> outbound queue -> provider outcome/recovery
```

A Main child closes only its own run; its terminal transition does not close an active parent workflow. CALLER delivery resumes ordinary authorized Main work before Main's terminal phase. Terminal repair cannot spawn a child or release a dependent mutation. Internal completion/recovery events are not external admissions and are never classified again.

O07 serializes each new join against the workflow's terminal-entry transition. Join first: membership and ordered intent revision advance durably, and the final covers that revision. Terminal entry first: membership stays closed, including throughout rejection/repair, cancellation, timeout and recovery; later input receives normal new-admission routing with current context/capacity/resource checks. A retry of an already joined admission keeps the original binding. A stale final candidate cannot settle a newer accepted intent.

An eligible active relation with an unavailable/unsafe continuation primitive stays under that ownership and the reviewed wait/reject/clarification policy. It cannot start a competing run. A pending nonterminal workflow may resume through a proven successor-run binding. After the interactive workflow is terminal, remaining physical or clarification state is explicit context for new routing; it does not reopen the old shared final.

Completion outcome is runtime-assigned: NORMAL accepts agent output; RECOVERED constructs complete trustworthy semantics from sufficient existing evidence; FAILED reports inability to establish those semantics while preserving known effects. All use O01 validation. A verified cleaning start can remain successful work without claiming physical completion. Explicit unavailable wording alone is not FAILED. Missing/malformed userResponse enters repair; only valid explicit-unavailable final-workflow completion is fallback-eligible.

Admission, capacity reservation, tool dispatch, physical effects, terminal acceptance, canonical final entry, payload freeze, queue custody and provider outcome require distinct evidence. No absence of progress events, elapsed timeout, model assertion or schema-valid placeholder substitutes for that evidence.

```text

  -> closed membership/intent + terminal phase/budget
  -> accepted record/outcome + trusted completion route
  -> final semantic message + canonical final entry
  -> frozen batch/native delivery identity -> queue/provider outcome/recovery
```

Record minimal versions, owner/action reason, provenance and phase transitions; input consumed/applied/uncertain status; denied stale/mutation attempts; actual task outcome separately from NORMAL/RECOVERED/FAILED; required result coverage; fallback eligibility/call outcome; frozen identity and native receipt/reconciliation. | Measurement | Denominator / interpretation |
| --- | --- |
| Routing and continuation | Evaluated genuine external admissions, split into joined/pending disposition, new Main route, new direct route, rejected/waiting and unavailable classification. Do not reclassify internal completions/retries. |
| Direct Main bypass | Delivered eligible direct workflows with zero Main inference / delivered workflows in that eligible cohort. Joined admissions do not multiply workflow counts. |
| False direct / false continuation | Independently adjudicated unsafe selections / selections of that type, plus / all labelled admissions, stratified by context/privacy/authority risk. Shadow decisions are hypothetical and dispatch nothing. |

| Capacity/resource safety | Reservation denials, stale-owner denials and uncertain-owner recovery by reviewed domain policy; observed violations are failures, not throughput trade-offs. |
| Response fallback | Valid unavailable final-workflow completions / accepted final-workflow completions; calls/failures per eligible fallback case. Invalid records are protocol failures, not fallback successes. |
| Finality and delivery | One shared completion/final entry/delivery identity per delivery-eligible workflow; provider delivered/pending/unknown outcomes counted per workflow identity, with membership traceable per admission. No per-admission final denominator. |
