## 1. Objective, scope, and acceptance boundary

Bring the existing Benson control plane into conformance with the approved architecture while preserving correct domain implementation. This plan replaces the previous stage instructions in this same file. Historical stage names identify evidence only; P01–P11 are the sole prospective execution sequence.

The Phase-1 target is one native canonical conversation across Main/direct execution, bounded admission-consistent routing context, deterministic continuation before ordinary routing, independently recorded admissions sharing one workflow final, isolated activations, mandatory domain/resource safety, one globally enforced completion protocol, one interactive final-response gate and a distinct policy-controlled nonterminal progress boundary, both using native delivery. Global cross-caller Agent Run capacity/admission control (O04), including quotas, durable capacity-pending work, FIFO/expiry, automatic promotion and universal pre-launch coverage, is deferred to later hardening; Section 6.7 retains the approved target.

Phase-1 plan acceptance requires the Phase-1 portions of Section 27.4, the stage criteria and the mandatory acceptance matrix below to have observed evidence. ## 3. Terminology, canonical owners, and transitions

| Term | Single meaning |

### 3.3 Control flow and irreversible boundaries

```text
native exact admission + canonical conversation custody
  -> bounded authorized context + trusted workflow/domain facts
  -> optional one-shot Decision evidence
  -> deterministic eligible-continuation check
       -> join/continue or proven existing lifecycle resume/wait/reject
       -> otherwise ordinary Main/direct routing and single commitment
  -> current domain/resource eligibility (global O04 admission deferred)
       +-> eligible pre-execution rejection -> Section 3.6 no-run final path; no activation
       +-> authorized execution -> atomic O05 ownership check/fencing before each mutation
  -> settle current run; bind reviewed completion policy and trusted disposition
       -> workflow-final eligible: atomically close membership/intent
       -> otherwise retain open workflow membership
  -> validate candidate; reject -> completion-only repair (execution closed)
       -> NORMAL, or runtime RECOVERED / FAILED from retained evidence
  -> Completion Control
       +-> nonfinal retention -> durable wait/recovery; no final response
       +-> CALLER -> authorized parent-workflow continuation
       +-> workflow-final/direct projection -> Response Controller
             -> eligibility and owner message / narrow fallback
             -> native prepare -> freeze -> outbound queue -> provider outcome/recovery
```

A Main child closes only its own run; its terminal transition does not close an active parent workflow. CALLER delivery resumes ordinary authorized Main work before Main's terminal phase. Terminal repair cannot spawn a child or release a dependent mutation. Internal completion/recovery events are not external admissions and are never classified again.

A domain run may also settle while its workflow waits for verified domain outcome. Trusted finality and the domain's completion scope determine whether its accepted result closes the workflow or records nonterminal progress. No direct projection may turn a start acknowledgment into the final of a workflow whose scope requires physical completion. Section 3.4 separates these lifecycle events; Section 6.7 separates mandatory resource safety from deferred capacity-pending policy.

O07 serializes each new join against the workflow's policy-eligible workflow-final entry. Join first: membership and ordered intent revision advance durably, and the final covers that revision. Workflow-final entry first: membership stays closed, including throughout rejection/repair, cancellation, timeout and recovery; later input receives normal new-admission routing with current context/domain/resource checks. A nonfinal run exit does not close joining; new joins still require current authority/phase checks and cannot steer that settled run. A retry of an already joined admission keeps the original binding. A stale final candidate cannot settle a newer accepted intent.

An eligible active relation with an unavailable/unsafe continuation primitive stays under that ownership and the reviewed wait/reject/clarification policy. It cannot start a competing run. A pending nonterminal workflow may resume through a proven successor-run binding. After the interactive workflow is terminal, remaining physical or clarification state is explicit context for new routing; it does not reopen the old shared final.

Completion outcome is runtime-assigned: NORMAL accepts valid run-origin output or a typed deterministic control-plane final under Section 3.6; RECOVERED constructs complete trustworthy semantics from sufficient existing evidence; FAILED reports inability to establish those semantics while preserving known effects. All use O01 validation. A verified cleaning start can remain successful work without claiming physical completion. Explicit unavailable wording alone is not FAILED. Missing/malformed run-origin userResponse enters repair; only valid explicit-unavailable final-workflow completion is fallback-eligible. Section 3.6's deterministic finals have usable policy-owned wording and no model repair/fallback.

Admission, domain ownership, tool dispatch, physical effects, terminal acceptance, canonical final entry, payload freeze, queue custody and provider outcome require distinct evidence; global capacity reservations are a deferred evidence class. No absence of progress events, elapsed timeout, model assertion or schema-valid placeholder substitutes for that evidence.

### 3.4 Workflow lifecycle across agent runs

The following are logical lifecycle states and transition requirements, not a new wire enum, store or lifecycle owner. O07 owns policy binding/membership/workflow-final closure; O08 owns each run's settlement protocol; O05 enforces mandatory domain/resource policy; O04 capacity accounting is deferred. Capacity-pending transitions below are a hardening target, not Phase-1 queue/promotion requirements. Existing clarification, WAITING_DOMAIN and authorized successor lifecycle remain distinct. Run finalization and workflow finalization are distinct under Section 3.5. Domain outcomes and NORMAL/RECOVERED/FAILED remain orthogonal. Section 6.8 progress emission is a self-transition for the same active run/nonterminal workflow, not the accepted run completion carrying progress facts in this table.

| State / event | Required workflow/run semantics | Capacity and resource consequence |
| --- | --- | --- |
| ADMITTED -> PENDING or EXECUTING | One trusted admission/commitment; a pending workflow retains intent, authority and idempotency without launching a waiting agent. Activation creates a fresh authorized run only after revalidation. | Phase 1 obtains required domain ownership atomically before mutation; busy Jessica work rejects without capacity-pending. Active/pending reservations and zero-Run quota overload belong to deferred O04. |
| ADMITTED -> FINALIZING -> TERMINAL (pre-execution rejection) | Section 3.6's trusted policy rejection closes the admission's workflow without creating a run. Record rejected outcome and explicit NOT_STARTED; construct the one deterministic final through O01/O08/O10/O13/native delivery. | No new active/pending reservation or domain effect. Never close or release another active workflow's ownership; terminal record/final recovery uses existing native state. |
| PENDING -> FINALIZING -> TERMINAL (without a new run) | Section 3.6's verified authorized cancellation, reviewed expiry or permanent ineligibility closes the workflow and all joined membership without inventing a run. NOT_STARTED requires proof of no prior execution; preserve any earlier settled run results/effects. | Fence activation and retire only this workflow's proven pending/undispatched reservations. Unknown launch or resource release stays with existing recovery. |
| EXECUTING -> WAITING_DOMAIN / PENDING | `benson_complete` settles the run with accepted start/progress/clarification facts while the workflow remains nonterminal if its reviewed close condition is unmet. Retain exact workflow/run/policy correlation, open membership and next state durably. Physical work may remain RUNNING with no live agent. | Retain physical ownership until its separate verified release predicate. Existing explicit clarification/domain waits do not create capacity-pending work. Active-capacity accounting and bounded capacity waits remain deferred. |
| PENDING / WAITING_DOMAIN -> EXECUTING | Supported native/domain availability evidence triggers revalidation of current authority, intent, conversation, workflow/generation and domain preconditions (capacity only after hardening); activate a fresh run only if needed and eligible. | Phase 1 permits only an explicitly authorized existing lifecycle successor, never automatic capacity-pending promotion. | Verified success -> FINALIZING -> TERMINAL | Finalize the workflow only for its actual completion scope, with atomic membership closure and one accepted final. ### 3.6 Deterministic activation denial and no-run workflow terminalization

An activation denial is not automatically a workflow terminal outcome. This complements Section 3.5 without changing run settlement or reviewed workflow-close conditions. Distinguish the following logical cases; no new tool, wire enum or persistent owner is selected. Pending cancellation requires authorized cancellation of the workflow under its requester/control policy, not merely an unrelated admission. Expiry requires the policy-bound expiry and current authoritative time; a wait timeout alone is not expiry. Permanent ineligibility requires a trusted domain/policy reason tied to current intent, generation and preconditions; transient resource unavailability permits truthful rejection/denial in Phase 1 without capacity-pending admission; bounded capacity waiting is deferred. Unknown policy, authority, dispatch or still-live execution stays with existing recovery instead of being declared terminal by this path.
