## 2. Evidence language and classification

- **VERIFIED CURRENT FACT**: observed read-only during this session, with the scope and time below. Source inspection proves code behavior, not that a running process loaded identical bytes or that hardware executed it.

**PROPOSED CHANGE:** keep exactly the existing native entry points `jessica_read` and `jessica_execute`; add closed discriminated branches, generated from one reviewed capability registry. ### 6.1 Reads

Extend existing `status`, `rooms`, `capabilities`, `maintenance`, `statistics`, `room_settings`, `operation_status` rather than creating synonyms. Return typed values, units, observed time, source time, source kind, availability/reason, and coverage. ## 7. Authorization, verification, and state invariants

### 7.1 Authorization

- Ordinary cleaning, verified settings and station actions retain the current equal policy for all five approved family members. Technical verification and authorization are independent checks.
- Trusted native requester identity, per-sender group verification, fresh child context, roster-policy agreement, and authorization run before device reads that could expose private data and before any write. Tool arguments/brief/HA labels cannot grant permissions.
- **Decision D3:** recommend owner-only destructive map edits, service maintenance/draining and consumable resets, with explicit semantics. This extends current `read`/`control` policy and is not already authorized. ### 10.2 Production human E2E protocol

Each physical acceptance uses one compact Oren handoff wherever possible. Before interrupting Oren, Sol completes implementation, focused/broader validation, runtime loading and the final read-only preflight, then provides:

1. **Ready state and exact interaction:** the passing preflight result, canary scope/expiry/action limit, exact natural prompt to send once and expected visible behavior. A failed preflight sends zero POSTs and creates no operator request.
2. **One evidence return:** Oren reports the physical observation and any manual cleanup/final state in one reply. Disagreement with the intended target/effect fails acceptance even if HA cache reports success.
3. **Autonomous deterministic verification:** Sol runs the bounded after-check for trusted identity, operation/request/plan digest, allowlisted payload, dispatch count, target/settings, evidence timestamps, applicable lifecycle correlation, result/final-answer consistency and absence of legacy/generic execution. Waiting and comparisons are deterministic, not model polling.
4. **Cleanup and uncertainty:** verify terminal/docked or agreed safe state, restoration/conflict status, locks/test scopes/delivery/jobs and no unintended future action. Never send an unsolicited compensating mutation after uncertainty; inspect side effects first and use only accepted cleanup paths.
5. **Promotion:** record the minimum durable evidence and exact equivalence class, remove expired test exposure, promote only the proven scope, update the ledger, and create one snapshot only if this is a meaningful accepted runtime/config milestone.

Read-only production acceptance uses the same path with an explicit assertion of no HA POST and no mutation record. Do not turn a battery/filter/status question into a vacuum action. Broad physical re-testing is unnecessary when durable accepted evidence and unchanged relevant code remain valid.

### 10.3 Observability requirements

Extend existing result/operation records rather than a new log store. Owner diagnostics include schema/registry/policy version, device/firmware/integration version/hash, trusted request key, native child/Automation occurrence, operation ID, plan digest, target/map/program generation, step claims and dispatch attempts, observed source timestamps, evidence origin/quality, applied settings/coupled effects, desired/observed state, uncertainty/reconciliation and restoration status, terminal outcome and acceptance reference. Audit exact payload safely without credentials or private geometry in ordinary user output.

The final Main response must distinguish requested/accepted/started/running/paused/returning/docked/completed, and persistent versus temporary settings. “Unavailable now”, “not production-enabled”, “unknown support”, “not authorized”, and “could not verify” are different outcomes. Include minimal useful facts and warnings, not internal traces. Owner-only diagnostic access remains existing architecture; no new notifier or messaging authority in Jessica.
